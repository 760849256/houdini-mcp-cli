下一阶段以“稳定连接、明确执行结果、减少操作等待”为交付目标。优先处理连接与任务生命周期，再优化日常操作路径。

保留现有 context / inspect / edit / execute / look / job 六个日常入口、Houdini 侧编辑开关和 Python 开关，兼容 advanced 接口。已有批量读取、上下文校验、Python job_id 去重和结构回读继续复用。

本阶段不以工具数量、单元测试数量或更换传输协议作为成效指标。先建立可重复的实际调用基线；完整迁移 DCC-MCP、重写 Rust 服务、扩展远程控制均放在后续独立决策中。

## 4. 目标架构与状态契约

近期保留当前本机 MCP → HTTP → Houdini 架构，按以下边界整理职责：

1. MCP 适配器：持续收发协议消息，管理客户端请求、实例绑定、短等待和结果摘要。
2. Houdini 侧 HTTP 工作线程：认证、接收请求、登记任务、提供不访问 hou 的存活与任务状态查询。
3. 有界主线程队列：串行执行场景 API，校验上下文和截止时间，完成结构回读。
4. 本地记录：保存实例租约、操作状态和脱敏诊断；重载和客户端断开后仍可追踪。
5. 可选独立进程：仅在原型证明有价值后承担宿主外监控、日志和连接管理；它不能让被计算阻塞的 Houdini 主线程继续执行场景操作。

所有读写以 session_id + generation 绑定一个具体 Bridge 实例。多次 RPC 不得在中途因默认记录变化而切换实例。HIP 新建/加载另有 scene_epoch；编辑还应检查目标节点身份及必要的前置状态。

连接状态至少区分：未启动、连接中、可用、主线程忙碌、重连中、已停止、进程退出、版本不兼容。主线程探针过期只说明近期未响应，不足以单独断言进程已死。

操作状态至少区分：已接收、排队中、执行中、已完成、部分完成、失败、已取消、结果待核实。结构验证与截图可用性独立返回。截图失败不得把已经完成的节点编辑误报成“完全未执行”。

## 5. 分阶段实施清单

### 阶段 A：建立基线与连接恢复（P0，预计 3–4 个工作日）

**A1. 建立实际链路记录**

- 每次调用记录 trace_id、session_id、generation、operation_id、命令类型和返回状态。
- 拆分发现、传输、排队、宿主执行、回读、序列化及整体耗时；HTTP 工作线程在任务完成前也要有接收记录。
- 日志按大小轮转，默认本地保存，避免记录令牌、Python 原文和完整场景数据。
- 提供一键诊断包：版本、运行状态、最近失败、任务列表、时序、连接变更原因。

**A2. 每实例注册与明确绑定**

- 从单个 session.json 迁移至按实例区分的记录；旧文件保留为兼容指针。
- 每条记录包含实例 UUID、PID、进程启动标识、端口、版本、租约时间和当前 HIP 摘要。
- 每实例使用独立临时文件并原子替换，解决多进程同时更新同一个 .tmp 的竞争。
- 启动时登记，停止时只撤销自身；客户端校验进程身份与租约，隔离过期记录。
- 当前绑定实例失效时，若存在多个候选，列出它们并要求明确目标；禁止自动把写操作移到另一个 Houdini。
- 先识别哪些运行中的 Houdini 已注册 Bridge；未注册的进程显示“Bridge 未启动”，不承诺仅靠外部重连即可恢复。

**A3. 分层健康与受控重连**

- 轻量存活接口只读线程安全缓存，不进入 hou；主线程用低成本探针更新 last_main_thread_tick。
- 查询连接状态默认不扫描场景、工具全集或工作流证据；完整诊断按需展开。
- 同实例服务重启后重新握手，更新 generation 和令牌；采用有上限、带抖动的退避，避免持续刷请求。
- 用户主动 Stop 后保持停止；只读恢复可自动进行，写操作先查询原 operation_id。
- 划分连接、接收、排队与执行预算，取消统一 5 秒的最终结果等待规则。

交付：可识别过期记录和多实例的连接层、状态面板、诊断包、实际链路基线。

阶段门槛：双实例互不覆盖；正常关闭及异常退出后不会继续宣称可用；相同实例服务恢复后可重新连接；无自动跨实例写入。

### 阶段 B：统一任务与生命周期（P0，预计 4–6 个工作日）

**B1. 普通编辑也有可查询任务**

- 将现有 Python job_id 机制推广到 edit、可能耗时的 inspect 和 look；统一 operation_id、请求摘要和结果查询。
- 宿主在任务入队前登记并返回接收确认；短任务可自动等待，超出短等待即返回原任务 ID。
- 同一 ID + 同一请求返回原状态；同一 ID + 不同内容拒绝。重连后按原 ID 查询。
- 任务状态持久化并有保留期限；适配器重启后恢复查询入口。
- 进程崩溃发生在场景修改和结果落盘之间时，标记“结果待核实”；不承诺跨崩溃恰好执行一次，不自动重放。

**B2. 有界主线程队列**

- 一个入口负责场景任务排序，限制队列长度和总等待时间，返回排队位置、忙碌原因及建议等待时间。
- 任务开始前重新校验实例、generation、HIP、权限、目标身份和前置条件。
- 已排队但过期或取消的任务不再执行，避免客户端早已超时后场景突然被修改。
- 网络、日志和结果状态处理可并发；所有要求主线程的 hou / Qt 操作继续串行。
- 取消支持排队任务及可协作检查的步骤；正在执行的任意 Python、cook 不提供强杀保证。
- 仅在明确可独立执行且场景依赖已保存时，才将缓存/渲染交给隔离 hython；不把实时场景写入直接搬到子进程。

**B3. MCP 收发和服务退出**

- 将 stdio 读循环与任务等待分离；长任务期间仍能响应 ping、状态与取消请求，stdout 统一串行写入。
- 明确处理取消通知，兼容客户端协商能力；进度通知可作为补充，任务查询必须独立可用。
- 启动/停止幂等；停止先拒绝新任务，处理队列，关闭连接，再限时回收工作线程。
- 禁止 Houdini 主线程等待一个正在等待主线程的工作线程；重载以 generation 使旧回调失效。
- 单独处理客户端断开和 BrokenPipe，不把“结果发送失败”混同于“场景操作失败”。
- 执行中重载默认延后或明确拒绝；停用编辑/Python 后，未开始的写任务必须重新检查权限。

交付：统一任务 API、可恢复任务列表、有界队列、可观测的取消与停止流程。

阶段门槛：响应丢失后不重复创建节点；排队超时后不发生延迟写入；客户端退出不拖垮 Houdini；长 cook 期间连接状态保持可解释。

### 阶段 C：缩短日常操作路径（P1，预计 3–5 个工作日）

**C1. 服务端完成一次编辑**

- 增加服务端 edit_batch，在同一实例和主线程上下文内完成目标解析、校验、执行及必要回读。
- 日常 edit 的初始 RPC 从至少四次减为一次提交；耗时任务通过原 ID 查询完成结果。
- 保留校验和上下文保护，避免重复全量校验；结构回读限定到实际受影响的节点与参数。
- 一个批次对应一个 Undo group，但不称为数据库式原子事务。中途失败返回已完成步骤、失败步骤和可用 Undo 信息。
- 针对现有 context_token 主要描述场景/选择身份的边界，补充目标节点身份和相关参数/连接前置条件；明确路径操作无需依赖无关选择变化。

**C2. 更少读取与更短响应**

- inspect 将上下文解析与 multi_read 合并；显式绝对路径读取在不依赖选择时跳过多余 context。
- 保留已有 fields、multi_read 和 cook 显式开关；进一步将字段筛选前推，避免先读取全部数据再裁剪。
- 节点/参数返回有界摘要、分页和截断标记；节点类型/schema 等静态信息可缓存，按版本及会话失效。
- 场景状态缓存注明时间和 revision；写入授权和上下文保护始终基于新鲜状态。
- 普通响应默认简明结果；详细审查和完整证据按需取用。测试各客户端对 structuredContent 和文本回退的要求后，再减少重复 JSON。
- 保留六个日常入口；高级能力可按需发现，不增加额外的日常操作步骤。
- 连接复用、长连接和协议替换只有在时序数据证明传输开销明显时才推进。

**C3. 截图可靠性**

- 统一可见 pane 的选择、截图完成等待和失败分类；附带来源、尺寸及可用性。
- 黑图/无可见视口继续明确报告，保留可用的网络图或结构结果；替代捕获方式须标明来源。
- 临时改变相机、视角、帧号和网络位置均需在异常路径恢复。
- 重复请求可合并；截图缩放、压缩及编码尽可能移到宿主 API 调用之后处理。

交付：同功能的低往返日常工具、简明输出、截图独立状态。

阶段门槛：同一基准下日常操作耗时、RPC 次数和响应体积有实测下降；结构保护和场景恢复行为不退步。

### 阶段 D：持续运行与灰度发布（P0 发布门槛，预计 2–3 个工作日及至少 2 个实际工作日观察）

- 在隔离 HIP 和真实 GUI Houdini 中测试，不使用生产场景做破坏性验收。
- 覆盖双实例、频繁 HIP 加载、新建场景、服务重载、Houdini 退出、MCP 客户端重启、电脑睡眠唤醒、长 cook、模态窗口、响应丢失和队列拥塞。
- 进行至少 8 小时持续运行、累计至少 1,000 次混合调用；长任务和故障恢复单独计数。
- 使用与日常客户端相同的 stdio → HTTP → GUI 主线程路径，不能只使用进程内 poster 或 mock。
- 先提供可回退的候选版本，记录至少 2 个实际工作日的断线次数、人工恢复次数和任务结果。
- 同一实例内支持新旧接口兼容；若新能力握手失败，明确提示功能限制，不静默退回缺少去重保证的写路径。

交付：版本固定的候选包、故障矩阵报告、性能前后对比和回退步骤。

## 6. 验收指标

以下是拟定目标，不是当前测量结果。阶段 A 固定基准后记录绝对数值和变化；如目标确需调整，应说明原因并保留原始数据。

| 维度 | 初始验收目标 | 测量边界 |
| --- | --- | --- |
| 轻量存活查询 | p95 ≤ 200 ms | 本机已建立连接；不访问 hou、不扫描场景。 |
| context | p95 ≤ 500 ms | GUI 空闲、已预热、无强制 cook。 |
| 20 个节点元数据读取 | p95 ≤ 1 s | 限定字段，无几何求值。 |
| 20 步简单节点/参数编辑及结构回读 | p95 ≤ 2 s | 隔离小场景，不含 cook、渲染、磁盘输出。 |
| 日常工具效率 | 固定混合任务集的集成开销较基线降低 ≥ 30% | 同机同版本；同时报告绝对时间、调用次数和响应体积，不能仅给百分比。 |
| 响应体积 | 固定任务集默认文本/结构数据字节数降低 ≥ 50% | 不以丢失错误、截断提示或必要回读实现压缩；模型实际 token 另测。 |
| 长任务 | 5 秒等待结束不再直接等同“执行失败”；已接收任务可查询 | 分别记录接收、排队、运行和结果状态。 |
| 自动恢复 | 同一目标的 Bridge 服务重新可用后，10 秒内恢复读取 | 不含用户重新启动 Houdini 或启用未启动的 Bridge 所需时间；多个候选不擅自切换。 |
| 幂等与隔离 | 故障注入中 0 次重复写入、0 次跨实例写入 | 分别覆盖发送前失败、执行后回复丢失、适配器重启和宿主崩溃。 |
| 持续运行 | 8 小时 / ≥ 1,000 次混合调用；无故障注入时非预期失败率 ≤ 0.1% | 预期拒绝、人工 Stop 和注入故障单列，不从报告中隐藏。 |
| UI 与生命周期 | 不新增死锁或崩溃；停止/重载后无遗留任务执行 | 线程、socket、回调数量在反复操作后无持续增长。 |
| 截图 | 可用视口下至少 100 次捕获成功率 ≥ 99%；不可用时明确失败 | 结合实际图片检查；黑图不得当成功，必须验证视角及网络恢复。 |

性能集包含小型约 200 节点、中型约 2,000 节点、大型约 10,000 节点三档场景；上表绝对时延先以小型场景验收，其余分档公布。每个常规场景至少 100 个样本，区分冷启动与预热，报告 p50/p95 和失败率。

端到端用户等待时间单独测量，包含模型思考和工具往返；Bridge 的集成开销需扣除宿主原生执行时间单独展示。对比 Blender/Unity 时，只比较可对应的连接恢复、往返次数及集成开销，不比较不同模拟或渲染任务的原始耗时。

## 7. 首批实施条目与后续决策

首个开发批次固定为：

1. 持久化脱敏时序与失败原因，建立实际链路基线。
2. 实例注册表、存活校验和单次操作的实例绑定。
3. 轻量存活接口与主线程响应探针。
4. 明确忙碌/离线/未启动，加入同实例重连及能力握手。

第二批统一任务和队列；第三批合并 edit/inspect 内部往返及压缩输出；通过持续运行门槛后发布。

总体估算：单人约 12–18 个工作日，实际 GUI 验收和灰度观察可与开发后段交叠。按阶段门槛推进；若 P0 尚有重复写入、跨实例路由或停止死锁问题，先修复再发布。

在阶段 B 后安排一个限定 1 个工作日的独立原型，对比：
- 在现有 Bridge 内补足监督与恢复。
- 将连接、日志和监控移至轻量宿主外进程。
- 复用固定版本的 DCC-MCP Core。

只在原型显示明确的稳定性收益、可接受的分发成本和兼容性时，另立迁移计划。Rust、WebSocket 或某个框架本身不构成稳定性与速度的验收证据。
